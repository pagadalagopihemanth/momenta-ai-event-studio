## Security and persistence

The original `webapi.app:app` remains local/single-user. Never expose that entry point or upload the owner's SQLite files. Public startup uses `webapi.public_demo:create_public_app --factory`.

Each browser receives a random HMAC-signed, Secure, HttpOnly, SameSite=Strict, host-only cookie. A dedicated SQLite file and proposal cache are scoped to that capability. Unknown, guessed, tampered or expired cookies cannot list, read, edit or export another workspace. Shared illustrative seed IDs refer to separate files. A stolen browser cookie is a stolen capability; this demo is not an authenticated production account system. Do not enter sensitive/real guest data.

Workspaces expire after 24 hours. SQLite files on the paid disk survive process restarts if the cookie and generated signing secret remain unchanged. Expired files are cleaned opportunistically; open handles and provider disk snapshots can retain physical bytes longer. Export PDF/CSV to keep work. Browser storage/cookie loss or signing-key rotation loses access. Unconfirmed previews can expire on cache eviction/restart.

Resource bounds: 100 active workspaces, 10 plans per workspace including three seeds, 60 API operations/session/minute, 300 admitted requests/process/minute, 128 KiB request bodies, ten-second body receive timeout, 64 MiB application data threshold, four in-flight child handlers, 16 cached child apps. These are demo abuse limits, not provider-level DDoS protection or an account-wide hosting-spend cap. Admission can temporarily reject new sessions if capacity is reached. Deploy only one worker/instance with these process-local limits.

Host and Origin are checked against the canonical HTTPS origin. Cross-site requests are rejected, responses are no-store, embedding is blocked, and a self-only CSP limits active content. API docs are disabled. The container build context is allowlisted and copies neither secrets, private records, reports, videos nor raw footage. React text rendering and existing Pydantic validation remain in use.

`MOMENTA_SESSION_SECRET` is the only deployment secret, generated by Render; never print it or add it to Git. `RENDER_EXTERNAL_HOSTNAME` supplies the canonical origin automatically. For a custom origin, explicitly set MOMENTA_PUBLIC_ORIGIN without a path. Storage is MOMENTA_DEMO_DATA=/var/lib/momenta. Verify the disk is writable by the container's non-root user during startup. No owner databases are migrated or mounted.

## Approval and deployment procedure

1. Review Dockerfile, .dockerignore, requirements-public.txt, render.yaml, public entry point and test evidence. The Blueprint passes Render's published JSON schema.
2. Obtain explicit approval to publish these changes, create one paid Render service and 1 GB disk, accept the stated ongoing cost, and expose the public offline demo. Authentication/account terms, if needed, are completed by the owner. No resource exists yet.
3. Run the final secret/privacy scan, commit deployment changes, and push normally to the approved repository. Do not force-push or modify old reviewed commits.
4. In the owner's Render Hobby workspace, create the service from the repository/Blueprint. Confirm price, Singapore, one instance, disk size and manual deploys. Stop if pricing differs or unapproved resource upgrades are required.
5. Ensure no OpenAI key or owner data is configured. Render generates the session signing secret. Do not copy .env.
6. Review build output and verify non-root disk permissions; build first, then startup health /api/health. Container build and Render startup remain unverified locally because Docker Desktop's engine is unavailable. No paid provisioning should be treated as guaranteed success.
7. Verify the actual assigned HTTPS URL (never invent the hostname): health, public notice, fresh signed-out desktop/mobile sessions, create/edit/rescue, persistence across restart, ownership isolation, impossible-budget rejection, PDF/CSV downloads and rejection of every live AI route. Confirm owner data is absent and no outgoing model request occurs.
8. Put only the verified deployed URL and exact deployed-update description into the submission package. LinkedIn and the PromptWars form remain separate, unapproved actions. Check hosting usage and suspend/delete resources when no longer needed, after owner approval.
